# Learning reflection

[Back to portfolio](../README.md)

## What I learned

The most useful change in my approach was recognising that a tool running successfully does not establish a vulnerability. I need to interpret what changed, identify the weakness and show evidence for the claimed impact. Packet captures, debugger observations and account identity checks were more useful when I connected them to a clear question.

## Most challenging work

Buffer overflows were difficult because I initially concentrated on completing the procedure. Breaking the investigation into input handling, memory overwrite, control flow and byte interpretation helped me explain why each step mattered. I still need more independent debugger practice.

## Ethics and professional judgement

Permission, privacy and accurate reporting are part of the technical work. I should keep activity within agreed scope, minimise disruption, protect collected data and report unsuccessful tests honestly. Potential impact should not be presented as an observed event.

## Where I want to improve

I want more practice in web/API authentication, session management and access control, along with stronger networking, Linux, scripting and debugging foundations. I am interested in connecting offensive testing with defensive monitoring: what a firewall, endpoint agent or application log actually records, and whether a proposed fix changes the result.

## Practice plan

Use guided labs to learn a technique, then repeat a related exercise with less instruction. Keep a journal of failed attempts and explanations. For each finding, write the evidence, impact, remediation and retest separately. Build a habit of measuring normal behaviour before applying a disruptive test.

## Feedback on learning structure

Clear setup prerequisites would help separate environment problems from conceptual problems. A gradual shift toward independent investigations, examples of strong evidence-led reports and more remediation/retest activities would make the work more useful.
