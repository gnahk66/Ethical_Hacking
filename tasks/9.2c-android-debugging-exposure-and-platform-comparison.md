## Objective
Explore the impact of authorised debugging access and reflect on Android/iOS security architecture.

## Tasks 1-4: PhoneSploit exercise
Installed and launched the tool, accessed the Android shell, explored directories and used `getprop` to inspect system properties. Recorded a screenshot operation and a remote power-off test on the lab device.

For the version shown in the submission, the documented menu options were **4** for a shell, **7** for screenshots and **10** for device power-off. These numbers are historical lab evidence, not a current universal menu reference.

An exposed debugging channel can enable powerful actions when its access requirements are met. This task does not show that PhoneSploit bypasses arbitrary Android authentication or grants control of any nearby phone.

## Tasks 5-6: platform comparison
Discussed application sandboxing, signing, permissions and inter-process communication on Android, alongside the layered security model presented for iOS. Reflected that Android's runtime, components and communication mechanisms felt more complex to analyse.

The source based its comparison on Vijay Kumar Velu's *Mobile Application Penetration Testing* (Packt, 2016). The conclusion favouring iOS was a reading-based opinion, not a current measured ranking. Both platforms have evolved substantially, so the comparison should not be used as present-day purchasing or security advice.

## Defensive recommendations
Disable unnecessary debugging, require authorised debugging hosts, restrict network reachability and revoke unused trust relationships. Use a dedicated lab device without personal accounts.
