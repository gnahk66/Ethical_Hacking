## Objective
Observe how unauthenticated local address mappings can enable interception and forged DNS responses.

## Method and evidence
- **B1-B3:** discovered lab peers, initiated the controlled ARP-poisoning test and compared address mappings on Windows and pfSense.
- **B4:** attempted to observe web traffic; changed to a plaintext HTTP test site when HTTPS prevented the intended inspection.
- **B5-B6:** used Ettercap's DNS spoofing configuration, cleared cached name-resolution data on Windows and checked the redirected test request.
- **B7:** analysed the capture. The write-up identifies frame 6561 as a response pointing the test domain to the Kali host, contrasted with upstream replies in frames 6565/6571.
- **B8:** considered both the exposure and relevant protective controls.

## Findings
The lab illustrates that a response claiming to come from a gateway is not authenticated merely by its source address. Comparing query details, answer content, timing and link-layer information is stronger evidence than one unexpected IP alone.

## Technical limits
Promiscuous mode cannot make a switch deliver all other hosts' unicast frames to the capturing interface. HTTPS protects application content and server identity when certificates are properly validated; an on-path position alone does not decrypt it. DNS spoofing also depends on matching outstanding queries and client acceptance, not simply winning any response race.

## Defensive recommendations
Use Dynamic ARP Inspection with trustworthy bindings where supported, monitor mapping changes, enforce HTTPS and use trusted validating DNS infrastructure. DNSSEC protects signed data when validation occurs; it is not universal protection for every local DNS path.
